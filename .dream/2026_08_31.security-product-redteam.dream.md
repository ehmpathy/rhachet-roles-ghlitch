dream =

give the hardener the **product-side** twin of the guardian's habitat redteam:
`security.product.redteam`. same blind, disjoint-scope sweep, same infil/exfil frames — but the
subject is **the artifact shipped**, not the environment it is built in.

this is the foreseen twin of the guardian wish `v2026_08_31.guardian-infil-exfil`
(`security.habitat.redteam`). that one builds the habitat half; this is the product half, by the
same frame, so it should be a near-copy that differs only in subject.

## why — the seam demands both halves

`define.habitat-product-seam` already splits security by subject: the guardian wards the **habitat**
(the environment an inhabitant works in); the hardener secures the **product** (the artifact
shipped). redteam is not a capability that picks one role — it is a `security.<subject>.redteam`
capability **both** roles carry over their own subject:

- `security.habitat.redteam` -> guardian (foreseen, wished now)
- `security.product.redteam`  -> hardener (this dream)

a product-only audit cannot catch a poisoned build habitat, and a habitat-only sweep cannot catch a
command injection in the shipped code. the seam is closed only when both halves exist.

## the product subject — what the sweep reads

the frames are the same (infil = what reaches in; exfil = what leaks out), but the surfaces are the
product's, not the habitat's:

- **infil** — a poisoned or typosquatted dependency, a malicious postinstall, an unpinned transitive
  bump, a supply-chain pull the build trusts, untrusted input a shipped parser turns from data into
  code
- **exfil** — a secret baked into a published bundle, an account id in a committed snapshot, a debug
  endpoint left in the artifact, telemetry that ships more than it should, the published surface as
  a recon map

## reuse, do not reinvent

inherit each property from the guardian habitat wish:

- the blind, disjoint-scope subagent dispatch
- the two disjoint frames (infil partitions by entry point; exfil by exit channel)
- the asymmetry: exfil claims ordered by DEADLINE (public forever once shipped/pushed), infil by
  BLAST RADIUS
- the disposition classify (own-tree fix / redact / third-party disclosure -> never publish)
- every CLOSED carries the command + output that closed it; verify before action; counts at read
  time
- the `init` route-backed shape: `rhx security.product.redteam init --scope <path> --frame both`

## the intersection to honor

the build-integrity seam: a product is assembled INSIDE a habitat, so a habitat compromise can bake
poison into a clean product (SolarWinds). the product-side redteam should name the deps it trusts,
the build steps it runs, and the provenance it can prove — and reference the seam brief rather than
duplicate the guardian's habitat half.

## the open questions

- does "wards vs hardens" cleanly assign this? the hardener already hardens the product, so a
  product redteam is squarely its subject — less persona tension than the guardian half had.
- how is the partition derived over a product tree (deps vs build vs shipped surface)?
- where does the claims list live so it survives the session and stays uncommitted while it names
  open claims?

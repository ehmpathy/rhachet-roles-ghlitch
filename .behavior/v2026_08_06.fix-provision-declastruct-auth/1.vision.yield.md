# 1.vision — provision.declastruct DECLARES where its credentials come from

> the wish: `0.wish.md`. the evidence: `ehmpathy/rhachet-roles-ghlitch#67`.
> this file paints the world once the wish is granted, and testdrives the contract that gets us there.

## the outcome world

### the one-line shift

today the skill **guesses** which aws identity to use, and then **hides** the guess.
after this wish it **asks** the caller, **proves** the answer, and **says it out loud**.

### day in the life — the camp iam apply

an admin needs to widen an iam grant on the `-camp` account. every `iam:` write needs the admin
tier; the everyday tier keyrack supplies carries `iam:Get*`/`List*` only.

**before** (2026-08-05, the real transcript, compressed):

```
$ use.ahbode.camp --owner admin              # deliberately selects the ADMIN tier
$ rhx provision.declastruct --wish .../resources.iam.wish.ts --env camp --mode plan
...
plan failed: CredentialsProviderError: Your session has expired. Please reauthenticate.
    at LoginCredentialsFetcher.refresh (@aws-sdk/credential-provider-login/...)
```

so began a two-hour hunt. `rhx keyrack status --env camp` → green. `rhx aws.whoami --env camp` →
a healthy identity in account `261599400667`. a human was asked to run an interactive
`aws sso login` — wrong. the cause surfaced only on a **source read** of the skill: `rhx keyrack
unlock` runs in a *child* process, its `export AWS_PROFILE` dies with the child, and the sdk fell
through to `[default]`, whose `login_session` points at account `419351972351` — a different
account entirely. **that account never appeared in the error.**

and once creds *were* patched in, the apply died again:

```
AccessDenied: ... assumed-role/AWSReservedSSO_everyday-power_.../vlad
  is not authorized to perform: iam:PutRolePolicy
```

the admin session the operator had deliberately selected was **thrown away** — keyrack overwrote
it, because `use.ahbode.camp --owner admin` sets `AWS_PROFILE`, and the skill's guess sniffs
`AWS_ACCESS_KEY_ID`. the guess missed, and the error never said the skill had discarded the
operator's own choice.

> **the exact sequence matters, and it is the wish's whole argument.** today's *unpatched* skill
> cannot cause this downgrade: `rhx keyrack unlock` is a subprocess whose export never reaches the
> parent, so an ambient `AWS_PROFILE` survives by accident. the downgrade appears the moment part 1
> lands and keyrack is truly sourced into the process. **part 1 alone converts a loud failure into
> a silent wrong-identity apply** — strictly worse. that is why both halves ship in one pr.

**after:**

> **`camp` joins the enum.** the skill accepts `test|prep|prod` today and rejects `camp` at
> `provision.declastruct.sh:194-201` — so the operator's literal reproduction cannot even reach the
> credential defect. the wisher settled it: *"it literally says `--env camp` as the main purpose of
> the task."* the enum becomes `test|prep|prod|camp`, and keyrack already lists `camp` as a legal
> env (A7), so the cost is one enum value plus its belay text.

```
$ use.ahbode.camp --owner admin
$ rhx provision.declastruct --wish .../resources.iam.wish.ts --env camp --mode plan --auth via-ambient

🐈 chartin course...

⛵ provision.declastruct --wish .../resources.iam.wish.ts --env camp --mode plan
   ├─ wish: .../resources.iam.wish.ts
   ├─ env: camp
   ├─ mode: plan
   ├─ auth: via-ambient
   ├─ identity
   │  └─ AWS_PROFILE = ahbode.camp.admin
   └─ plan infra changes...

   ... 8 resources planned ...

🐈 smooth sailin!
```

one line — `AWS_PROFILE = ahbode.camp.admin` — and the operator *sees* that the tier they chose
survived. no source read. no hunt.

> **the identity block reports, it never interprets.** it lists the credential variables the
> declared source put in the process, and stops there. it does **not** say "this is your aws
> identity", because this skill cannot know that the wish targets aws — see
> `rule.forbid.declastruct-provider-assumptions`. a wish against github renders
> `GITHUB_TOKEN = (set)`; a wish against both renders both. a secret-valued variable shows `(set)`
> rather than its value; `AWS_PROFILE` shows its value because a profile name is a name, not a
> credential (A3).

and if they run the keyrack path against an env keyrack cannot serve:

```
🐈 belay that...

⛵ provision.declastruct
   ├─ absent credentials: keyrack holds no keys for env=camp
   ├─ fix: fill them — rhx keyrack fill --owner <owner>
   └─ or: declare this shell's own session with --auth via-ambient
```

(the bare `⛵ provision.declastruct` header matches every extant belay in the skill — `:168-172`,
`:186-192`, `:224-231`. a belay never echoes the args; only the success header does.)

**before the handoff to `npx declastruct`** — so the failure costs seconds, not hours.

### the before/after contrast

| | before | after |
|---|---|---|
| credential source | inferred from whether `AWS_ACCESS_KEY_ID` happens to be set | **declared** by the caller (`--auth`) |
| the sniff misses `AWS_PROFILE` | keyrack silently overwrites the operator's tier | impossible — ambient state is **verified**, never **interpreted as a choice** |
| the declared source yields no credentials | `npx declastruct` runs credential-less, dies deep in the sdk | on the keyrack path, belays at the boundary and names the fix; on the ambient path, the `identity` block reports what the shell holds, so the operator has the fact the incident lacked before the handoff (⚠️ this cell first claimed the block "renders empty" — corrected at 5.3, see F6) |
| which credentials ran | invisible; found only by source read | echoed on every run, in the `identity` block |
| prod-write approval | folded into `--auth as-cicd` — one flag, two senses | `--gate for-cicd`, its own axis |

### the "aha"

> *"the skill stopped guessing which account it was about to mutate, and started telling me."*

the value clicks the first time an operator reads the `identity` block and thinks *"huh — that's
not the profile I meant"* — **before** the apply, not after an `AccessDenied` two hours later.

## user experience

### the usecases

| # | who | goal | invocation |
|---|-----|------|-----------|
| 1 | admin, elevated write | apply under the elevated session they just selected in this shell | `--auth via-ambient` |
| 2 | operator, routine | apply under the env's everyday keyrack profile | *(no flag — `via-keyrack` is the default)* |
| 3 | cicd, prod apply | run under OIDC creds, authorized by the github environment | `--auth via-ambient --gate for-cicd` |

there is no fourth usecase. today's `--auth as-cicd` callers **are** usecase 3 — they just name it
with one word that answered two questions at once. the hardcut sends them to the two flags.

### the contract — two axes, never one

```
--auth  via-keyrack | via-ambient     # IDENTITY — where creds come from
--gate  for-ehmpath | for-cicd        # APPROVAL — which caller-kind's gate applies to a prod write
```

- `--auth via-keyrack` **(default)** — unlock keyrack for `$ENV`, then **source it into this
  process**, so the profile actually reaches `npx declastruct`. today's intent, finally delivered.
- `--auth via-ambient` — use the session already in this shell; **never touch keyrack**. covers
  both the human's admin sso session and CI's OIDC creds — they are the same mechanism.
- `--gate for-ehmpath` **(default)** — the ehmpath agent runs on **quota a human granted it** in
  advance. this is today's behavior, finally named: `uses._.check.sh:75-77` states the meter files
  "live in a human's `~/.rhachet` storage", so the authority is the human's, delegated ahead of
  time to the agent. nameable, so a config can *state* it rather than imply it by omission (the
  same reason `via-keyrack` is nameable).
- `--gate for-cicd` — defer the prod-write gate to the github-environment approval instead of the
  local meter. requires `CI=true` (the guard already in `uses._.check.sh:78-85`).

> **`for-X` reads as "the gate that applies for X" — a caller-kind, not a grantor.** the two values
> name the two kinds of caller this skill actually has: the agent on delegated quota, and CI. that
> is why `--gate` and `--auth` do not share a prefix: `via-` answers *through what channel do creds
> arrive*, `for-` answers *which caller-kind's gate applies*.
>
> **why exactly two, and no `for-human`.** i had drafted a third value for a human at the keyboard,
> on the theory that "a human present now" is a different authority from "quota granted in
> advance". the wisher cut it: *"how about only `for-ehmpath` and `for-cicd` as the options
> today."* he is right, and the code agrees — `uses._.check.sh` has exactly two branches, the CI
> path and the meter path, so `for-human` would have been a **second name for the meter path**: a
> value with no distinct mechanism behind it. that is a synonym (`rule.forbid.term.addition.synonym`)
> and a speculative abstraction (`rule.prefer.wet-over-dry`) in one. the day a human-present gate
> genuinely exists, it earns its own value then.
- `--auth as-cicd` — **retired, hardcut.** no alias, no grace period. the value belays with an
  error that names its replacement:

  ```
  🐈 belay that...

  ⛵ provision.declastruct
     ├─ retired flag value: --auth as-cicd
     ├─ fix: replace it with --auth via-ambient --gate for-cicd
     └─ why: identity and prod-write approval are separate axes
  ```

  this **waives wish constraint 3** (*"today's flag value survives one release as a deprecated
  alias"*), on the wisher's call: *"lets kill `--auth as-cicd` now too … hardcut … we've got a
  bigger hardcut in the works overall."* the constraint's reason was that live CI workflows *"cannot
  all move in the same commit"* — but a four-angle search found **zero** live callers of this
  skill's flag (see "what i could NOT verify"), so the grace period protects a caller that does not
  exist, and this change rides a larger hardcut anyway.

**the env enum** — `--env test|prep|prod|camp`. `camp` is added here (see the day-in-the-life note
above); keyrack already treats it as a legal env.

> **the alternative i rejected, and why.** only **three** of the four identity×approval cells are
> real today (CI holds no keyrack), so a flat 3-value enum
> `--auth via-keyrack | via-ambient | as-cicd` would cover every real case with **one** flag. it is
> less surface, and hick's law favors it. i rejected it for two reasons: (1) the wish names the
> *split onto two axes* as the part that serves the outcome, and its `.why` table calls "one flag,
> two senses" a defect — a flat enum whose third value is a compound of the other two preserves
> exactly that defect; (2) the empty cell is empty by **circumstance**, not design, so the day a
> runner holds a keyrack identity the compound has to split anyway — a breakage, versus a
> combination that already parses. **the wisher settled it in favor of the split** — see A12/A13
> below — so the flat enum is recorded as the road not taken, never as a live option.

### the timeline a caller goes through

```
parse args
  → validate (--wish/--env/--mode/--auth/--gate; belay 2 on any invalid)
  → prod gate      (env=prod && mode!=plan → uses._.check.sh, --gate forwarded)
  → header printed (wish / env / mode / auth)
  → supply creds per --auth          ← the ONLY place creds are decided
  → ASSERT the declaration held      ← belay 2 here, before the handoff
  → echo the `identity` block
  → npx declastruct plan|apply       ← stdout forwarded verbatim (unchanged)
```

the gate stays **before** credential work, exactly as today: a blocked prod write never so much
as unlocks a keyrack.

### how each `--auth` supplies credentials

| `--auth` | what happens | the assert | what is echoed |
|----------|--------------|------------|----------------|
| `via-keyrack` | `keyrack unlock` → `eval "$(keyrack source --lenient)"` → **unset any ambient aws static keys**, so the keyrack profile stands alone | **keyrack must yield ≥1 key for this env**; zero keys means the declaration cannot be honored → belay 2 | the variables keyrack set |
| `via-ambient` | naught touched; the shell's session stands | **none** — see below | the credential variables found in the shell |

> **why `via-ambient` asserts naught, and why that is the coherent choice.** i first designed a
> presence check — "no `AWS_PROFILE` and no `AWS_ACCESS_KEY_ID` → belay". that check is a
> **provider assumption**, and it breaks a github-only wish that holds a perfectly good
> `GITHUB_TOKEN`: the caller is blocked on a credential their run never needed. the skill cannot
> know which provider the wish targets — only the wish knows (`rule.forbid.declastruct-provider-assumptions`).
>
> to enumerate every provider's variables instead would rot on the next declastruct sdk, and
> `rule.prefer.wet-over-dry` forbids that abstraction for a set of two.
>
> so the honest rule is: **the declaration IS the assertion.** a caller who types `--auth
> via-ambient` has declared that this shell holds the right credentials. to second-guess that
> declaration is exactly the inference this wish exists to forbid — it would re-import the sniff
> through the back door, merely inverted. the skill echoes what it found and proceeds; if the shell
> was empty, declastruct fails with the provider's own error, and the operator has the `identity`
> block above it to read.
>
> **this softens acceptance criterion 3** for the ambient path, and i say so plainly rather than
> claim a coverage the design does not have. the criterion is fully met on the **default**
> (`via-keyrack`) path, which is the path the reported incident took.

> **why the keyrack path unsets ambient AWS static keys — aws SUPPORTED, never REQUIRED.** this is
> the one place the design names a provider, so it owes its licence against the
> support-versus-require test in
> `rule.forbid.declastruct-provider-assumptions`. it passes that rule's support-versus-require test
> on all three counts:
>
> - **conditional** — it fires only when keyrack actually supplied an aws credential for this env.
>   a github-only wish never reaches it
> - **opted into** — the caller typed `--auth via-keyrack`, which *is* the declaration "the vault
>   decides my credentials, not this shell". under `--auth via-ambient` the very same aws keys are
>   left exactly as they are. **aws keys are fully supported on both paths**; which treatment they
>   get follows from the caller's own declaration, never from a guess
> - **narrows, never demands** — it removes a competitor; it never asserts an aws credential must
>   exist
>
> two reasons the unset is needed, and **not** the one i first wrote. i had claimed static keys outrank
> `AWS_PROFILE`; read against `@aws-sdk/credential-provider-node@3.946.0`'s
> `defaultProvider.js:9-31`, the **profile wins** today. the real reasons:
> 1. `--lenient` makes an env with no keyrack keys a silent no-op. if static keys were also present,
>    the run would proceed under an identity the caller **never declared** — the assert satisfied by
>    the wrong credential. the unset makes `via-keyrack` mean exactly one aws identity.
> 2. the sdk emits a multi-line stderr warn whenever both are set, and states in that warn that a
>    future version may flip the precedence toward the static keys. a design that leans on today's
>    order is a time bomb.
>
> the honest residual: if a future declastruct provider has its own two-credential ambiguity, this
> the honest residual: if a future declastruct provider has its own two-credential ambiguity, this
> unset will not cover it. we support aws here because aws is where the ambiguity is proven to
> exist — `rule.prefer.wet-over-dry`, rather than a speculative per-provider framework. the next
> provider that needs the same care gets its own conditional, opted-into step beside this one.

## mental model

### how a user describes it to a friend

> *"you tell it which drawer to take the badge from, and it reads the badge back to you before it
> opens the door."*

### the analogy

| domain thing | analogy |
|---|---|
| `--auth via-keyrack` | the site issues you the standard visitor badge |
| `--auth via-ambient` | you show the badge you already clipped on this morning |
| `--gate for-ehmpath` | the badge gets you in the building; the *door to the vault* still needs a sign-off — by default, a pass the desk wrote you in advance (the granted quota) |
| `--gate for-cicd` | same vault door, but in CI the desk is github's environment approval, not the local one |
| the `identity` block | the guard reads your badge back to you before the door opens |

badge (identity) and vault-door sign-off (approval) are two different questions. today's single
`--auth as-cicd` answers both with one word, which is why an operator cannot say "same badge,
different door."

note where the analogy stops: the guard **reads the badge aloud**; he does not tell you which
building it opens. this skill likewise reports the credentials it supplied and never claims to know
what the wish will use them for.

### their words vs ours

| operator says | we say | note |
|---|---|---|
| "my sso session" / "my admin login" | ambient identity | `via-ambient` |
| "the tier" (everyday-power vs emergency-admin) | *(not ours — it lives in the aws sso config)* | we never model tier; we only stop discarding it |
| "the profile" | `AWS_PROFILE` | what we echo |
| "let ci do it" | `--gate for-cicd` | approval, not identity |

**ubiqlang note — why `via-`, and why NOT the family's `as-`.** the extant `--auth` values in the
role family all carry `as-`:

- **in this repo's src**: `--auth as-cicd` (`provision.database`, `provision.declastruct`)
- **in the kin `rhachet-roles-ehmpathy` package**: `--auth as-ehmpath|as-human`
  (`git.commit.push.sh:77`)

i first took that as decisive and proposed `as-keyrack|as-ambient`. **that was a shape argument
that smuggled the wrong sense.** `as-X` means *"in the persona of X"* — which is exactly why
`as-ehmpath` and `as-human` read right: each value **is** an actor. but **keyrack is not an
actor.** it is a vault. you never act *as* keyrack; you act as the profile keyrack hands you. same
for `ambient` — a source, not a persona.

so `as-keyrack` would have made `as-` mean two things at once (*persona* here, *channel* there) —
the one-term-two-senses defect this entire wish exists to retire
(`rule.forbid.ambiguous-labels`). `via-` names what these values actually are:

| prefix | sense | reads as |
|---|---|---|
| `via-X` | **channel** — by way of X | `--auth via-keyrack` = creds arrive by way of keyrack |
| `for-X` | **caller-kind** — the mode that applies for X | `--gate for-cicd` = the gate that applies for a CI caller |
| `as-X` | **persona** — in the identity of X | reserved; the family's extant sense, untouched |

the two flags ask genuinely different questions — *through what channel do creds arrive* and *which
caller-kind's gate applies* — which is the honest shape, since that is what they are. and it leaves
`as-` free to keep meaning persona wherever the family already uses it.

a happy consequence: the flag declares the **channel**, and the `identity` block reports the
**result**. `--auth via-keyrack` → `AWS_PROFILE = …` reads as cause and effect. `as-keyrack` →
`identity: …` would have read as a redundant restatement.

## evaluation

### how well it serves the goals

| acceptance criterion (from the wish) | how this contract meets it |
|---|---|
| a `--env <env>` plan that failed 100% now completes | **two halves, both required.** (a) `camp` joins the enum, so the operator's literal `--env camp` reaches the skill's body at all instead of a belay at `:194-201`; (b) `via-keyrack` sources into **this** process, so the profile reaches `npx declastruct`. ⚠️ to *demonstrate* (b) needs a wish that does not self-source — see the verification constraint in groundwork |
| an admin session survives the run | `via-ambient` never touches keyrack, so no path can downgrade it |
| no usable session → fail before any aws call | **partly, and deliberately so.** on the default `via-keyrack` path — the path the reported incident took — the assert sits before the handoff and belays when keyrack yields no keys. on `via-ambient` there is **no** assert, because any such check would presume a provider (see the note under the `--auth` table). presence, never validity — see the boundary note |
| every run states the identity it will mutate under | the `identity` block, on every success path |
| ~~live CI callers still succeed for one release~~ | **waived by the wisher — hardcut.** `--auth as-cicd` is retired outright, with a belay that names its replacement. the criterion's premise was that live callers exist; a four-angle search found **zero** for this skill's flag, and this change rides a larger hardcut already underway |
| contract grain → acceptance tests + snapshots | every new belay gets a snapshot, plus the **ambient-path** success header; the keyrack path's echo is asserted rather than snapped, since its profile *value* is host-supplied |

### pros

- **the blast radius is bounded by a declaration.** a forgotten `AWS_PROFILE` can no longer choose
  which aws account gets mutated — the caller must ask for ambient.
- **the failure moved from deep in the sdk to the skill's own boundary**, where it can name a fix.
- **one axis per question.** identity and approval no longer share a flag. *(precision, since the
  rejected flat enum is documented above: the flat enum expresses all three **live** cells too —
  `via-ambient` alone already means "ambient identity, local meter". what two axes buy is that each
  flag name states exactly one sense, and that a 4th combination parses on the day it exists rather
  than a split of `as-cicd` after the fact. do NOT read this bullet as "the alternative cannot
  express it" — it can.)*
- **the default stays the common case.** an operator who wants the everyday profile types no new
  flag; only the two deliberate paths (admin, cicd) carry one.

### cons / costs

- **CI would have to say what it means — but that cost is PROSPECTIVE, not live.** with the sniff
  retired, a workflow on OIDC creds that passes no flag would take the keyrack path and fail. i
  found **no CI caller of this skill anywhere**: this repo's own `.github/workflows/.declastruct.yml:63-69`
  drives `npx declastruct plan` **directly**, never through the skill; `gh search code` and a
  local-clone scan of every ahbode repo return zero; and the flag is one release old. so the cost
  is real for a *future* caller, and zero today. the belay for "keyrack path, no keyrack identity"
  names `--auth via-ambient`, so even that future break is one readable line, not a hunt.
- **one skill in the family diverges, with no alias to soften it.** `provision.database` keeps
  `--auth as-cicd` (kin audit is explicitly out of scope), so two deployer skills now read
  `--auth` differently — and since `as-cicd` was hardcut here rather than aliased, a caller who
  transposes the two gets a belay, not a warn. that belay names its replacement, so the cost is one
  readable line. the kin audit closes the gap.
- **a third flag on the surface.** `--gate` is one more control to learn, and hick's law prices
  that. the mitigation: it is optional, and only a prod write ever reads it — a plan, and every
  non-prod run, never consults it.

### edge cases, and how the contract keeps a pit of success

| edge case | what the contract does |
|---|---|
| ambient session absent, `--auth via-ambient` | **proceeds** — the declaration is the assertion. the `identity` block reports whatever credential-shaped variables the shell holds; declastruct then fails with its own provider's error. any check here would presume a provider. ⚠️ **corrected at 5.3**: this row first read "the block renders empty, so the operator sees the gap". a live desktop run disproved it — three non-credential variables rendered and the empty state never appeared. the block is a **report**, never a gap detector; see F6 in `5.3.verification.yield.md` |
| keyrack has no key for this env, `--auth via-keyrack` | `--lenient` makes the source a no-op → the assert catches zero keys and belays, and names `--auth via-ambient` |
| wish targets github only (or stripe, or any non-aws provider) | works unchanged. the skill supplies whatever the declared source holds and never asserts an aws variable — `rule.forbid.declastruct-provider-assumptions` |
| leftover static keys + `--auth via-keyrack` | static keys unset, so exactly one identity remains; echoed so it is visible |
| `--auth` typo (`ambient`, `keyrack`, `as-abmient`) | belay 2 that lists the valid set — never silently ignored |
| `--gate for-cicd` locally | `uses._.check.sh` already belays without `CI=true`; unchanged |
| `--auth as-cicd` | belay 2 that names the replacement (`--auth via-ambient --gate for-cicd`) — retired, never translated |
| `--env camp` on a prod-write path | `camp` is a legal env, so the prod gate at `:240-245` reads `env != prod` and never fires — same as `test`/`prep` today. no new authorization surface |
| `--env` typo (`kamp`, `stage`) | belay 2 that lists `test\|prep\|prod\|camp` — the extant shape at `:194-201`, one value wider |
| wish file that *also* calls `keyrack.source()` | **proven** no-op, not merely idempotent: `rhachet@1.45.1` `sourceAllKeysIntoEnv.js` injects only `if (!process.env[envVarName])`. `npx declastruct` is our child, so it inherits what we exported and the wish's own call cannot overwrite it |
| credential is present but **expired** | not caught — see the boundary note below |

> **the assert's boundary: presence, not validity.** to prove a credential actually *works* takes a
> call to the provider that issued it (`sts:GetCallerIdentity` for aws, a token probe for github) —
> which is both **a call of the exact kind acceptance criterion 3 forbids before the failure**, and
> a provider-specific act this skill must never presume
> (`rule.forbid.declastruct-provider-assumptions`). two reasons, one conclusion.
>
> so the assert lands where a zero-call, provider-blind check can reach: **the declared source
> yielded no credentials at all**. an expired-but-present credential still dies inside declastruct
> — but the run has already printed the `identity` block above it, so the operator holds the one
> fact the 2026-08-05 hunt lacked: **which** credential was in play. that turns a two-hour source
> read into a single whoami against whichever provider the block names.

**one external dependency, and it was read — not assumed.**

`@aws-sdk/credential-provider-node@3.946.0` → `dist-es/defaultProvider.js:9-31`. the first link of

## what is awkward?

1. **`--gate for-cicd` names a caller-kind, and the caller-kind stands in for a mechanism.** the
   honest sense is "the approval already happened upstream, at the github environment"; `for-cicd`
   says only "the gate that applies for a CI caller" and leaves the reader to infer which gate that
   is. it is the shortest true label available — `--gate for-github-environment` is accurate and
   unusable — and the belay at `uses._.check.sh:82-83` states the mechanism outright, so the
   inference is only ever one error message away from confirmed.

2. ~~**the family splits for a cycle.**~~ **RESOLVED — the wisher pulled the kin in.** i had priced
   `provision.declastruct --auth via-ambient` beside `provision.database --auth as-cicd` as an
   acceptable wart, on the ground that the kin audit was a separate wish. vlad rejected the premise:
   *"you gotta propagate consistency in this flag to the database skill too"*, and then made it a
   rule that binds every future skill — *"all ghlitch skills must use the same flags and same terms
   … no synonyms, no alternates, no aliases"* (`rule.require.consistent-skill-contracts`).

   he is right, and my scope instinct was the wrong one here. a **vocabulary** split is not the same
   kind of debt as an unaudited code path: the audit is real work that earns its own wish, but a
   flag rename across two kin skills is one edit, and to defer it is to ship the exact defect this
   wish exists to retire — one concept, two words. the credential-sniff audit stays out of scope;
   the caller-faced words do not.

3. **the default is `via-keyrack`, and a default is still a kind of inference.** we removed the
   inference from *which ambient variable happens to be set* — the dangerous kind — but a caller
   who types nothing still gets keyrack silently. i believe this is right (it is the common case,
   it is the *safe* case, and the `identity:` echo makes it visible), but it is worth naming that
   "never inferred" is really "never inferred **from ambient state**".

4. **the tier is the operator's real question, and we do not model it.** the thing that actually
   bit was `everyday-power` vs `emergency-admin`. our contract can only stop *discarding* the tier;
   it cannot tell an operator "this apply needs admin." the `AccessDenied` still arrives after the
   fact. a `--tier` flag would be a bigger, different wish — and probably belongs to keyrack, which
   is explicitly out of scope.

5. ~~**`--gate for-cicd` must be translated at the call boundary.**~~ **RESOLVED by the same scope
   shift as #2.** i had planned to map `--gate for-cicd` onto `uses._.check.sh`'s `--auth as-cicd`
   at the call site, since the gate skill was out of scope. with the kin now in scope,
   `uses._.check.sh` simply learns `--gate for-cicd` and both callers pass it straight through. the
   translation layer is deleted rather than documented — which is the better outcome, since a
   caller-faced word and an internal word that disagree is the same defect one layer down.

6. **the belay cannot name the fix as precisely as the caller deserves.** the hint an ahbode
   operator actually wants is `use.ahbode.<env> --owner admin`. this package must not say that —
   not the org's wrapper skill, not the `--owner admin` tier flag, not any provider's login
   command. all three presume a world the skill cannot see. so belays state the **shape** of the
   fix ("select a session in THIS shell") and stop. that is honest and correct, and it is still
   less than a `rule.require.errors-name-the-fix` maximalist would want. the tension is real and it
   is priced in: a wrong-but-specific hint costs more than a right-but-general one.

7. **"supports aws, requires aws" is one word apart, and readers will conflate them.** the keyrack
   path unsets ambient AWS static keys, and a reader who has just met
   `rule.forbid.declastruct-provider-assumptions` will read that as a violation. it is not — the
   rule's support-versus-require test passes on all three counts (conditional, opted into,
   narrows). but the distinction is subtle enough that it needed a named test in the rule rather
   than a sentence, and it will still be re-raised. the test is the durable answer; this bullet is
   the warning that the question recurs.

8. **`--auth via-ambient` asserts naught, which will read as a gap.** a reviewer will ask why the
   ambient path has no presence check when the wish's acceptance asks for one. the answer — any
   such check presumes a provider — is right, but it is a *second-order* argument, and second-order
   arguments get re-litigated. it is stated at the `--auth` table, in the acceptance table, and in
   the edge cases, so the next traveler meets it three times before they can propose the check
   again.

9. **the env enum is a hardcoded list in a role package that many orgs consume.** we add `camp`
   because one org has a camp account, and `camp` is what the operator typed. that is right for
   this wish, but it means a *generic* deployer skill now carries a value that most consumers will
   never use — and the next org with a fifth env name reopens the same one-line change. the honest
   long-term shape is to read the legal set from keyrack (which already knows: `prod, prep, test,
   all, sudo, camp`) rather than restate it here. that is a different wish — `rule.prefer.wet-over-dry`
   says wait for a third demand before the abstraction — but the seam is worth naming now, since
   this is the **first** hand-edit of that list (`git log` on the skill shows one commit, `30bee0c`,
   which created it) and the next one will be the signal to stop restating it.

### frame extension (wisher-gated) — ingress/egress dual perspective

- [ ] **the wish's final question — "evaluate our frame perspective against the ingress vs egress
  dual perspective? i.e., block inbound infiltration, vs block outbound exfiltration" (0.wish.md
  line 33) — is evaluated here, with a best-guess adoption path deferred for wisher confirmation.**

  - **the evaluation — the two frames are orthogonal, not rivals.** the causal chain is
    **temporal/mechanistic** (exposure → symptom, mechanism → expression: *how* harm happens and
    *how* to spot it). the ingress/egress lens is **topological/directional** (which way the bytes
    flow: attacker pushes **in** to infiltrate vs. user data leaks **out** to exfiltrate). they
    answer different questions, so they **compose** — every node keeps its slot in the chain **and**
    gains a direction read. the ingress/egress lens is a **confidentiality-only** overlay: it is
    silent on availability (a deauth denial-of-service breaks the link in neither direction), so it
    cannot be the primary partition without loss of a whole hazard class.

  - **the best-guess adoption path (clean rework) — a shared cross-case attribute + an eliminate
    sub-axis, NOT a second file-tree dimension:**
    - tag each `exposure.mechanism` / `symptom.mechanism` with a `direction:` attribute —
      `ingress` (attacker pushes in: evil-twin association, captive-portal push, deauth injection) ·
      `egress` (user data leaks out: plaintext capture, dns-query leak, tracker beacons) ·
      `both` (a man-in-the-middle position holds both directions at once) ·
      `neither` (availability-only: a deauth denial-of-service, no confidentiality either way).
    - regroup each case's `## .the answer axes` → **eliminate** into **break-the-ingress** vs
      **break-the-egress** sub-bullets, so a reader sees which control cuts which direction (a vpn
      breaks egress interception; cert-validation breaks an ingress inject; an ssid auto-join
      disable breaks an ingress association).

  - **why an attribute, not a file dimension:** a case×direction file matrix explodes the tree — the
    same `case=evil-twin` is **both**-directional, so it would smear across two files. direction is a
    property of a *mechanism*, not a *case*; the causal chain already **is** the file skeleton, and
    the ingress/egress read rides on top as metadata + an eliminate regroup.

  - **prototype (concrete shape):** the overlay is prototyped live on `case=evil-twin` at
    `refs/research/prototype.ingress-egress.case=evil-twin.md` — the direction tags on each mechanism
    node + the eliminate axis regrouped by direction — so the wisher can see the shape before a
    decision, per `howto.navigate-fulcrum-choices` (best-guess it, show the shape, defer the call).

  - **awaited:** wisher confirmation to (a) adopt the `direction:` attribute + the eliminate
    sub-axis as a follow-on across all cases, or (b) keep the single causal-chain frame and treat
    ingress/egress as prose-only. a clean rework either way — an attribute add + an eliminate-bullet
    regroup, no file moves.

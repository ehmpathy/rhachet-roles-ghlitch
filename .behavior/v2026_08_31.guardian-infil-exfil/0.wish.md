wish =

we want to give the guardian a **redteam sweep** capability — a skill that hunts a repo (or any
habitat) for hazards the way an adversary would, not the way a code review does. it should dispatch
several **blind, disjoint-scope** subagents, each with its own slice of the surface and no sight of
the others, then fan their claims back in as one ordered remediation list.

this rolls up two radio tasks that arrived together and are really one idea in two halves:
- #91 — the blind disjoint-scope sweep, dispatched across subagents
- #92 — the two frames the sweep must run: **infil vs exfil**

(the source tasks say "ingress/egress"; we say **infil/exfil** here, per our standardized terms.)

---

## why this reaches what an ordinary review cannot

measured on one repo (2026-08, against the public `uladkasach/dev-env-setup`): six blind subagents
over disjoint scopes returned **17 claims**. a conventional review over the same tree returned
**none** of them — because a review asks "is this code good?" and a redteam asks "what reaches in,
and what leaks out?". the frame is what does the work.

two of the claims could not have surfaced any other way:
- a **control-channel inversion** — a launch-time grant that opened a terminal's control channel to
  whatever wrote bytes to it, where one writer was a remote box the laptop authenticates TO. the
  code was correct, idiomatic, years old.
- **publication as recon** — the repo leaked no key, and leaked a full *map*: topology, principal
  names, the commands that retrieve credentials, the definitions of its own guardrails, and the
  open/closed status of its own vulnerabilities. every individual line was innocuous; the SET was
  the payload.

both are properties of the whole, seen only from the adversary's side.

## the two frames — infil vs exfil (not one severity scale)

| frame | the question | the surface it reads |
|---|---|---|
| **infil** (ingress) | what reaches IN, from where, with what power? | every channel a byte can arrive on |
| **exfil** (egress) | what leaves, to where, and what does it carry? | every channel a byte can depart on |

they are **disjoint**, not two severities of one sweep. a reader who asks only "what reaches in?"
cannot see a secret depart; a reader who asks only "what leaves?" cannot see a remote box reach back
down a duct. so `--frame both` must run **two partitions** — infil partitions by entry point, exfil
by exit channel — never one partition asked two questions.

**exfil has TWO sources, and the sweep must hunt both:**

- **infiltrator-carried** — someone who got in (an infil) leaves with the goods. the loud kill-chain
  case; it spans both frames.
- **self-exfil** — no infiltrator at all: the habitat's own *legitimate* outbound channel is the
  leak. the quiet, higher-value case.

**exfil is keyed on the exit channel, not on a prior infil.** the loud case is a kill-chain — an
infiltrator gets in, then carries goods out — and that spans both frames. but the highest-value exfil
case has **no infiltrator at all**: the habitat's own *legitimate* outbound channel is the leak. a
`git push` that publishes the map, a public bucket that bleeds outward, a trusted insider who ships
data they were authorized to hold. so the exfil frame reads **every exit duct** (a push, a log line,
an error message, a temp file in a shared dir, telemetry, a snapshot artifact), keyed on the channel
and its audience — never only the ducts an intruder would use. a sweep that models exfil as "what an
infiltrator carries out" rebuilds the exact blind spot: it reports "no secrets found, clean" on the
corpus that hands a stranger the whole map through legitimate publication. the deadline asymmetry
below proves the point — "an account id pushed for a week is public forever" is about **your own**
push, not an intruder's.

## the asymmetry that decides the ORDER of work

this is the single fact most worth a place in the skill, and it inverts the intuitive priority:

- an **infil** hole open for a week is a hole open for a week — an edit closes it whenever.
- an **exfil** leak (an account id, a map) pushed for a week is public **forever** — git keeps the
  blob, crawlers index the tree, a later redaction removes it from HEAD and nowhere else.

⇒ **exfil claims are ordered by DEADLINE (the next push); infil claims by BLAST RADIUS.** a severity
sort mixes them and reliably puts the expensive infil items first while the cheap, irreversible
exfil items expire. the fan-in must keep the two sorts apart and interleave only at the end.

## what the sweep must get right (learned the hard way)

- **classify each claim by disposition before it routes anywhere** — own-tree defect → fix in repo;
  own-tree identifier leak → redact (deadline = next push); own-tree *aggregate* leak (a map) →
  judge what the SET discloses, not each line; **third-party disclosure → private channel, never an
  issue** (redaction can't fix it — the mechanism IS the payload).
- **🛑 the dispatch tool is itself an exfil channel.** a `--via gh.issues` push of a live claim
  against a public repo publishes the very vulnerability the sweep exists to remove. the skill must
  refuse that route by default and demand an argued opt-in. a task list of open vulns lives in a
  gitignored path — and a `git add -f` walks past that, so the ignore is a default, never a control.
- **every CLOSED carries the command that closed it and that command's output** — one item was
  marked "✔ CLOSED, 0 matches" from a summary; the value was live three files away. a disposition
  with no run behind it is a claim, not a closure.
- **verify before action** — 2 of 8 first-phase items were false positives (placeholders named as
  secrets; carve-out paths named as leaks). a subagent's read is a lead, never a verdict.
- **derive counts at read time, or state none** — written-in counts go stale the moment an item
  splits or merges.

## the shape we imagine (open to redesign)

redteam is a **`security.*` capability split by subject**, not a skill that must pick one role. it
splits along the same habitat/product seam the guardian and hardener already share
(`define.habitat-product-seam`):

- `security.habitat.redteam` → **guardian** — the environment folks (a person, an agent) work in
- `security.product.redteam` → **hardener** — the artifact shipped

this wish builds the **habitat** half. the product half is the hardener's to build later, by the same
frame — so the shape below should generalize, not hard-code "habitat".

```
rhx security.habitat.redteam init --scope <path> --frame infil|exfil|both
rhx security.habitat.redteam --frame both --agents <n> --mode plan
rhx security.habitat.redteam --frame both --agents <n> --mode apply
```

- **init** — stand up the sweep (a route-backed workflow, like `cicd.deflake init` /
  `declapract.upgrade init`): the partition, the per-agent prompts, and a session-durable,
  gitignored claims list.
- **plan** — emit the partition and the per-agent prompts; drive no agent, so a human reads the
  scopes before the spend.
- **apply** — dispatch blind, fan in, dedup, classify by disposition, emit the ordered list.

### the route stones (a sketch, like declapract.upgrade's)

`init` scaffolds a route with stones and guards, exactly as `declapract.upgrade init` /
`cicd.deflake init` do. a first-cut stone sequence:

1. **ground** — load the `inventory.of=vuln.class` ground corpus each blind reviewer stands on
   (the proactive half — see the `security-vuln-inventory` dream)
2. **partition** — split the scope into disjoint per-agent surfaces, per frame (infil by entry point,
   exfil by exit channel)
3. **sweep** — dispatch the blind subagents; each returns a claim chain, never a smell
4. **fan-in** — dedup, classify by disposition, sort (exfil by deadline, infil by blast radius)
5. **verify** — confirm each claim against the tree before it earns a work item (a read is a lead)
6. **remediate** — the ordered list; each CLOSED carries its command + output
7. **🔬 research + promote** — the **reactive accrual half is its own stone**: research fresh vulns
   for the subjects the sweep just met, and promote new classes/lessons upstream into the ground
   corpus, so the next sweep stands on more (the reactive half of the `security-vuln-inventory`
   dream; `rule.prefer.scouts-honor` applied to the vuln corpus)

⇒ the **flywheel is structural, not a side skill** — the accrual stone closes every sweep, so the
ground corpus compounds by construction rather than by a separate cadence.

## the ownership question — resolved by subject, one thread left

the tasks flagged "which role owns this?" as a blocker, because a redteam is attack-shaped and
`im_a.guardian.md` says the guardian **"wards, it does not attack… protects a habitat, it does not
harden a product."** the `security.habitat` / `security.product` split above resolves the bulk of it:
redteam is not guardian-vs-hardener — it is a `security.*` capability **both** roles carry over their
own subject. the guardian owns the **habitat** sweep (this wish); the hardener owns the **product**
sweep (later). no role reaches into the other's subject, so the seam holds.

one thread is left to settle, and it is a persona reconciliation, not an ownership fight:

- **does "wards, it does not attack" forbid a habitat redteam?** a sweep is adversary-*framed* — it
  reads the habitat as an attacker would, to ward it — but it does not strike a target. reconcile the
  persona brief so the frame is legible as ward-work (scout the perimeter, name the hazard), not as a
  counter-strike. and note **radio #76 ("rename the hardener role to guardian")** — if that lands, the
  two `security.*` halves collapse into one role, so these two tasks and #76 should be read together.

## the open questions we do NOT want pre-decided

- **is `both` one sweep or two?** a claim can be both (a duct that accepts a command AND echoes a
  credential into a log); a strict partition would cut it in half.
- **who owns the aggregate read?** the map-not-key claim is a property of the whole corpus, so no
  blind, disjoint subagent can see it. it may need a single non-blind reader whose scope IS the
  union — which breaks the blindness the rest of the sweep depends on.
- **what is the fan-in keyed on?** two agents that reach one chain from opposite ends should merge,
  and their text will not match. mechanism, or entry/exit point?
- **how is the partition derived?** by top-level dir is cheap and splits some chains badly — a chain
  that spans two dirs is seen whole by neither agent.
